来源为 RCWL-9610 V3.0，第 4/5 页。用户明确该 PDF 不是实板 A 版手册，以下仅描述旧资料，不用于证明 A 版的时序、量程、电源或反馈电阻要求。

| 项目 | 手册 | 当前 UL |
| --- | --- | --- |
| TRIG | 高电平大于 10 us | 约 50 us，符合该条件 |
| ECHO | 约 20 ms 盲区处理后输出，脉宽正比距离 | 等上升沿，再捕下降沿计算；正常 20 ms 延迟在 70 ms 等待预算内 |

即使对旧版而言，70 ms 也是表中典型周期，不能误写成明确最小间隔，更不能据此宣称 A 版必须 70 ms。现有代码没有相邻 TRIG 的最低间隔，存在提前重触发的可能；按旧版 20 ms 延迟输入估算的 22/45/56 ms 不是 A 版实测。固定 80～100 ms 只建议用于排查过早重触发的对照实验，并非已核实的 A 版强制周期。

## 已复现的固件计时竞态

代码位置：`UL/firmware/app/Src/main.c:46～51`、`UL/firmware/app/Src/cs100a.c:49～64,68～92`。

主循环先取 `now_ms`，处理 UART 后才调用 `cs100a_poll(now_ms)`。在此期间 TIM14/TIM1 IRQ 会更新 `state` 和 `state_started_ms`。如果主循环使用的旧时间为 100 ms，而 IRQ 已写入 101 ms，`(uint32_t)(100-101)` 变为 `0xFFFFFFFF`，立即满足“至少 70 ms”的超时条件；WAIT_RISE 分支随即 `publish(0, NO_ECHO, now_ms)`，将距离发为 0。

同样的差值用于 GUARD，也能让回波刚结束就提前触发下一次测量。`state` 和时间戳不是一致快照，另有 IRQ 在条件判断期间完成测量、主循环仍按旧状态发布超时的竞态窗口。因此只在 main 多读一次时间并不能完整消除状态交错；后续修复需一致获取时间/状态，并在提交超时或启动动作时保证状态仍匹配。

使用当前**未修改**的 `cs100a.c`、真实 `cs100a.h/board.h` 和最小 GPIO/时钟/IRQ 桩，在 `UL/tests/build/rcwl_diagnosis` 用 VC98 编译并执行，结果：

```text
CONTROL: normal WAIT_RISE timeout at 70 ms
REPRO: IRQ timestamp=101, old poll=100, elapsed=0 ms -> status=4 distance=0
REPRO: 20 ms delayed valid ECHO, next TRIG at 22 ms, not 70 ms
REPRO: old poll timestamp skips 1 ms GUARD after IRQ sample publish
```

这些证明现有代码可以在并未经过真实超时的情况下产生 0，但尚未证明现场每个 0 都走同一个交错路径。

其它需核实的代码风险：TRIG 高电平期间的 ECHO 上升沿会被忽略；由于 A 版时序尚未取得，不能按旧版 20 ms 延迟排除该路径，需测 TRIG/ECHO 波形。极性切换后清 CC1 有窄窗口丢下降沿风险，更偏向短脉冲。500 kHz 的 16 位计数约 131 ms，正常数米脉宽远小于该值，正确使用无符号差值不因普通回绕变 0。

## 网页中的 0 实际代表什么

板端明确写 0 的路径主要是：启动 NONE、WAIT_RISE 超时 NO_ECHO、极短捕获计数 0/1 导致换算为 0 且标 TOO_CLOSE。高电平超时目前上报 33000 ticks/11220 mm 并标 OUT_OF_RANGE，不是直接 0。

主控 `external_ports.c` 对 GET_SAMPLE 的 `distance/ticks/status` 原样解码。主控 0.9 的 `tools/status_dashboard.py:250` 对在线 UL 无条件显示 `distance`，没有按 `sample_status` 将无效结果显示为“无回波”，所以 NO_ECHO 的占位 0 变成“0 mm”。Python 距离条件另有 VALID/在线/样本年龄检查，不能直接将网页表现等同于程序把无回波当作 0 距离比较。

本轮只读现有 `http://127.0.0.1:8765/api/state`，不另开串口。25 s 观察窗口取得 P1 的 30 条不同日志快照（不是全部声学样本）：28 条 ST=1，2 条 ST=4，2 次 0 的 ticks 都为 0、设备均在线。零值序号为 47668、47880；主机 TO/FE/UE 从头到尾保持 4600/5/61，没有增长。有效距离约 186 mm。期间有 3 次 HTTP 读取超时，这是网页读取层的问题，不能当作串口错误，也不能把该窗口称为无丢失采集。

此前主控工作树的 `docs/verification_20261029_sensors_live.md` 也记录同 UID 的 57 条日志中 5 条 D=0/ST=4。两次证据支持：用户看到的 0 是驱动“未捕到有效回波”状态，不是有效的 0 mm。尚不能区分每次是实际无回波、触发被忽略、漏捕边沿还是软件误判。

## 建议的处理顺序

1. 优先修复计时/状态竞态，并用当前复现用例做回归；不要只把 70 ms 超时调大。
2. 用固定 80～100 ms 相邻触发周期作保守对照实验，不把该值称为 A 版规定；按触发开始计周期间隔，且等待 ECHO 回低，不只增加“结束后 1 ms”。取得 A 版时序或测得正常波形后，再确定最高稳定刷新率。
3. 观测页按状态显示 VALID 距离、NO_ECHO、OUT_OF_RANGE、NONE/离线，禁止把无效占位 0 呈现为有效距离。若保留上次有效值，应同时明确过期标记和时间，不能悄悄滤掉失败。
4. 保留已确认的 75 kΩ，不依据旧手册贸然改阻值。远处继续异常时，用平整正对墙面做分档测试，取得 A 版推荐接收放大电路与探头资料；对照记录 TRIG、ECHO、sample_status、echo_ticks 和错误计数。弱回波、接收增益/噪声或饱和都是待测可能，不能仅由 75 kΩ 判定，更不能单独解释近距离固定目标也偶发 0。

以上为诊断及建议，未实现修复或烧录新固件；当前板上仍为此前 1.0.1 应用。后续实现时需同时更新实际芯片资料、驱动参数及显示标签，不应继续用旧“CS100A 8 m”或旧“RCWL9610 6 m”作为 A 版实板的量程承诺。
