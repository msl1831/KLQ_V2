## 当前观测

修订版冷启动后 SWD 读到 CPU 正常运行、无 CFSR/HFSR 故障。USB CTRL=`0x9C08`、ADDR=`0`；PA12 输入为高、PA11 为低，复位回调计数为 0。Windows 仅显示 DAPLink 的 COM92，没有机器人 USB 串口。计数是控制器回调观测，不等同于 USB 总线抓包，不能单凭这一项断定数据连接问题。

正在区分 USB 软件初始化、Windows 设备状态与实际连接状态。用户指出早期确实显示过 KLQ BOOT；既往 INFO/ECHO 与应用下载结果支持继续优先做软件回归。参考原理图与实板是否完全一致尚未确认，不能据图纸疑点认定硬件故障。

## 首次成功版本回归

- 恢复官方初始化（不主动断开 D+）及官方 suspend 流程，重新写入后仍未枚举。
- 进一步恢复首次成功烧录时的源码，包含原先 30 ms D+ 断开流程。源文件保存在 `diagnostics/usb_first_success/`，可用 `tools/build.py --usb-baseline` 重建。
- 当前板载对照镜像为 9452 字节，已逐字节读回验证，SHA-256：`6801ec4f97a95c4d1392e2e386bb865762f93fd2585a072af6275262920c69b9`；新构建入口的产物与已烧录对照镜像完全一致。
- 回归版本仍未枚举，控制器 ADDR=`0x80`，复位回调为 1。官方 suspend 主动切换 FORRST 会生成内部复位事件，因此该计数不代表主机 RESET。
- Windows 保留 `USB\VID_314B&PID_0108\000000000000`、COM123 的离线记录；尝试只移除这一设备实例并重新扫描时，PnPUtil 返回“拒绝访问”，没有执行成功，已请求用户在管理员窗口运行。这不是删除驱动，也没有重启整个 USB 主控制器。

## 已做的软件调整

- USB 端点缓冲区使用不重叠的 PMA 地址。
- SDK suspend 处理改为非阻塞。
- 初始化前拉低 D+ 300 ms，USB 模拟部分上电等待 2 ms，控制器准备好后释放 D+。
- DAP 烧录脚本补充 `reset_and_halt()`。此前直接在原固件运行状态下启动 Flash 算法曾产生 HardFault；使用 pyOCD load 成功恢复并读回校验。脚本修订后的完整重写流程还需实测。
